Greybeard · design discovery · round 1

What should a PR look like when the greybeard reads it?

Three visual directions for the review-map page. Every board uses the same sections and the same sample chapter, so the differences come from the direction itself. The sample PR, file names and code are demonstration material.

Who and what

An author self-reviewing an AI-written PR in a browser, usually on a laptop beside the editor. One job: understand every chapter well enough to explain it.

Want

  • Reads like a guided explanation, not a file list
  • Connections are visible next to the code they belong to
  • A senior's voice: calm, a bit dry, never cute

Avoid

  • A GitHub clone with a new coat of paint
  • A dashboard of big-number tiles
  • Mascot noise that gets in the way of reading code

Fixed by the product

One offline HTML file, light and dark, keyboard-first, mostly code and short prose. The diff stays the main object on screen.

Direction A

The Margin

The page is a glossed manuscript. The changed code sits in the centre column. What it connects to (callers, importers, tests) sits in the margin beside it, the way a Talmud page or a Tufte handout puts commentary next to the line it explains. Greybeard writes in red pencil.

Motion and interaction

Almost none. Hovering a margin note draws a thin line to the exact code line it refers to. j/k move between chapters; the margins re-align. Marking a chapter as understood adds a small pencil tick.

Fails when

The screen is narrow: the margins fold under the code and the gloss idea weakens. A chapter with many connected symbols crowds the margin. The serif-plus-paper look can read as "literary" if it isn't kept cool and precise.

Direction B

The Route

The PR is a journey with stations. A transit-map rail on the left shows the chapters in dependency order, coloured by layer (types, core, wiring, tests, config). The current chapter fills the page, and its connections show as transfer lines to other stations. Greybeard is the conductor: short, factual announcements.

Motion and interaction

The rail is the navigation: a filled dot for each chapter you've understood, and the line fills as you progress. Hovering "Imported by" highlights the stop it leads to. Moving between chapters slides the main panel; reduced-motion swaps that for a cut.

Fails when

A PR has 12+ chapters: the rail gets long and the metaphor turns into a list with dots. Five line colours plus diff red and green is a lot of colour. Closest to "a nice product UI", so the character carries less weight.

Direction C

The Printout

The PR is printed on tractor-feed green-bar paper and handed to the greybeard, who scribbles on it in blue pencil. Everything is monospace and dense like a listing; only his notes are handwritten. Dark mode is an amber phosphor terminal. It's the most character-forward option and speaks straight to CLI people.

Motion and interaction

Pure keyboard: j/k, n next chapter, x mark understood (stamps "OK" in pencil). A one-time paper-feed scroll on load, off under reduced motion. Nothing else moves.

Fails when

Long prose (summary, PR description) is tiring in monospace. The handwriting face can feel gimmicky after the first day. The paper texture fights syntax highlighting, so colour in code has to stay minimal.

Recommendation

Start from A, The Margin, and borrow B's rail

The product's core idea is "this block, and what it connects to". The Margin is the only direction where that idea is the layout: connections sit beside the exact lines they belong to, which is what the research says reviewers lack. A small version of B's route rail could carry navigation and progress without taking over. C has the strongest character; its ASCII mascot and pencil notes could appear as the greybeard's voice inside A rather than as the whole page.

Questions for round 2:

  1. Which direction (or mix) feels closest to what you'd want to open on your own PR?
  2. How loud should the greybeard be: quiet margin notes (A), short announcements (B), or a visible character with ASCII face and handwriting (C)?
  3. Do you mostly review on a wide screen? A depends on room for both margins.
  4. Anything you've seen (a tool, a site, a printed thing) that feels right or wrong for this?

Talmud design and the Internet

An argument, not a layout spec.

Tufte CSS

Sidenotes that sit next to the line and fold away on small screens.

Don't copy the cream and serif look as a whole.

Proofreading marks

Red pen plus margin note: a correction lives beside what it corrects.

No literal proof symbols in the UI.

Sourcegraph Diff Tour

Sections in a suggested reading order, progress tracking.

Their layout isn't public; we only borrow the ordering idea.

Graphite Code Tours

Narrative next to the diff, as if an engineer walks you through it.

Don't copy their product chrome.

Breaking the Alphabet (ICSE 2026)

Research, not visuals.

IBM Plex Mono
